# E-P7 配方 Wi-Fi 协议状态：未发布 / 阻塞

**截至 T25 本轮，没有 v4 接收端，没有可使用的配方协议，也没有 v4 安装包或预期包哈希。**
本文是发布闸门与字段契约记录，不能作为相机端点说明；T26b 的真实读取、备份、写入、还原和模拟相机实现均不能据此假定一个已实现的接收端。`EP7HL1` 仍只是 Issue 的建议名称，原厂 HTTP 200、未知属性的零值、已有 v2/v3 或原厂可调 S 都不构成能力确认。

## 为什么没有命令表

T25 在存储提交/发布、应用空闲准入和完整持久化生命周期上未通过验证。此时分配一个 CGI 路径、数字属性或“成功”返回值，会让后续客户端把设计草案误当相机能力。没有指定 HTTP 方法、URI、能力查询编码或可发送错误码；禁止回退到 `set_mcon`、原始记录写入或 40 次未经事务审查的标量编辑。

| 操作 | 当前状态 | 发布前必须验证 |
| --- | --- | --- |
| 能力查询 | 未实现，无合法请求编码 | 原厂拒绝；v4 精确返回型号、协议版本、范围、槽数与能力 |
| 读取完整槽 | 未实现 | 读取已提交的同一槽/版本共 40 值；不是 ACTIVE 中途 staging 数据 |
| 写入完整槽 | 未实现 | 完整解析/校验后才允许首个写入；应用任务准入与 payload 所有权可证明 |
| 保存结果 | 未实现 | 分部 API、已注册设置、刷新、一次正常保存和错误传播/重载闭合 |
| 超时 / 断连 | 未定义线上错误码 | 明确是否已入队、是否可能仍在执行；不能伪造取消或自动重试 |

现有原厂路径的已验证位置见 [T25 证据](../research/t25-storage-and-wifi-evidence.json)。它们仅是原生研究边界，不是一个可以直接写 H/L 的公开 API；也不能照搬 PEN-F HSL1。

## 已确定的应用字段契约（不等于线上格式）

沿用 [ep7-film-recipe-v1](recipe-format.md)，按该文档的轮盘顺序。将来相机协议的 40 值逻辑顺序固定如下；线上编码、封包、校验、大小和端点仍须接收端验证后定义：

| 索引 | 含义 | 单位 / 第一版范围 |
| --- | --- | --- |
| 0…11 | 12 色 H | 滑块整数 −7…+7 |
| 12…23 | 12 色 S | 滑块整数 −5…+5 |
| 24…35 | 12 色 L | 滑块整数 −7…+7 |
| 36 | 阴影 | 档位整数 −7…+7 |
| 37 | 中间调 | 档位整数 −7…+7 |
| 38 | 高光 | 档位整数 −7…+7 |
| 39 | 创意暗角 | 档位整数 −5…+5 |

槽为 COLOR1…4，由请求单独指定，不改变配方文件格式。名称、说明及 WB、WB 偏移、EV 文字建议不写进相机。编辑滑块、枚举序号、原生有符号值并非同一层单位，不能直接把 wire 中的整数交给一个未验证的原厂 setter。

候选存储单元的实验编码是 `0xe741CCVV`：VV 低/高有符号 4 位分别为 H/L，CC 为 VV 的补码字节。−8、非法标记/版本/补码、非 u32 全部按中性解码。225 组轴值已做原创合成测试；这只是未安装的候选，不是已发布 v4 数据格式，更不是事务或持久化保证。

## T26b 的依赖闸门

在本文件明确改为“已由 v4 接收端验证”并给出固件身份、完整命令表、成功/错误语义及原生端到端证据之前：

1. 不得开发或发布一个声称能写入 E-P7 的客户端；不得以只通过自制 mock 证明相机协议存在。
2. 不得为避免阻塞而猜测 URI、能力字符串响应、错误码或保存命令。
3. 若后续另行授权仅开发离线客户端原型，必须单独命名为模拟协议，生产网络路径保持禁用，并且不能把它作为 T26b 实机功能验收。

建议先补上 E-P7 提交后发布与空闲编辑的真实连接，再冻结协议；候选 A 仍可继续验证，独立 SD 文件也需要同样的准入与发布条件，不能绕过这些闸门。
