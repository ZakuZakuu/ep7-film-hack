### MN103 language feasibility

The fixed upstream [mn103.sinc](https://github.com/txt231/GhidraMn10300/blob/f89c1f469f07df31afea5dbf9e7c9057deba7b4a/data/languages/mn103.sinc) has commented UDFU01 definitions (lines733–735), relevant to the existing opaque descriptor traversal0x28fb05; SAT16/SAT24/BSCH use mn_todo (lines637–639). CALL semantics contain speculative stack compensation (lines583–600), and direct CALLS uses a memory store through MDR (lines606–607) rather than the assignment used in indirect CALLS (line605). These are **verified source hazards**, not measured runtime mismatches. Licensing and unvalidated call/stack/loop/extension semantics make raw pseudocode unsafe for object-lifetime work. AM33/FPU stubs add another gap.

Admission for a future language needs explicit redistribution/use rights, exact GNU instruction boundaries/operands/direct targets on the limited producer/receiver/classifier corpus, independently documented register/stack/return/condition semantics, and P-code tests for known byte/halfword loads, masks, hardware loops and extension instructions. Percentage decoded is insufficient. Stop on any boundary/flow/width disagreement, disable unsupported semantics, and do not begin a large bespoke SLEIGH implementation without a separate engineering decision. REA would additionally need an MN103 target adapter; fixing Node alone cannot admit E-P7. The npm6.4.0 publisher reports gitHead a56f7bb668ab23fec8d33f7af353ac7ed2fe1895, distinct from the audited c22111e source snapshot. Its actual analyze help exposes only DOS COM target-format, and a benign raw MN103 request rejects --architecture as UNKNOWN/Unknown flag. The newer source documentation is not evidence that those flags shipped in the installed release. Both identities are recorded separately.

## Decision and next stage

**Continue infrastructure-supported, source-grounded offline analysis; do not yet invest in ART extension/installation.** G1 holds; G2 remains incomplete, G3/G6 untested and G4/G5 NO-GO. Nothing here proves accepted color grain, actual preview/JPEG consumers, independently saved named filters, resource expansion, modified-update acceptance or recovery.

Highest-value next problem is admitting **MN103 call/stack/hardware-loop/extension semantics and a scoped loader** so object lifetime and indirect registrations can be reasoned about reliably. Resolve module licensing first or select a properly licensed maintained implementation; validate synthetic semantics against architecture documentation and known E-P7 boundaries. This is a finite admission experiment, not a surprise compiler project.

For ART specifically, require an independently referenced source-record creator/registration that accounts for group/type/mode, source+20 effects, source+24 Type and now source+33 secondary byte. Then examine writes/persistence and an actual preview/JPEG consumer. An arbitrary text name, raw call candidate, generic initialization or field presence is insufficient. If no justified registration/record anchor appears, stop that route; do not resume T6/classifier/downstream chains to populate the index.
