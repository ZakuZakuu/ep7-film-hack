# T27：删除键路由、数值显示与机内提交边界

任务没有完成：缺的是经过验证的机内 H/L 提交闭环和 v5/v5a 实现。
这轮证明了怎样让删除键事件穿过原厂状态机，到达真正的 COLOR 控件。
也证明原厂数字控件只能显示 0–5，并验证了可传递 `L +7`、`H -7` 的另一条原生文字路径。
色轮经过两种方法仍未定位；由于其余功能也未完成，本轮不能称为“仅缺色轮的 v5a”。

- 基线为包含 PR #72 的 main；遵循 [机主补充](https://github.com/ZakuZakuu/ep7-film-hack/issues/70#issuecomment-6470726983)，删除键循环 S → L → H，ALL 和长按 OK 必须保留。
- 新证据、完整哈希、地址和限制见 [本轮 JSON](t27-ui-flow-evidence.json)；[PR #72 证据](t27-in-camera-editor-evidence.json) 保留，不能把其中的旧降级设计继续当要求。
- 上游仅参考 [PEN-F 设计](https://github.com/fishcu/oly_fw_analysis/blob/539fcf1fa9eda5fdef8ede4deeab94a4691d94c3/docs/color/pen-f/EDITOR.md) 及配套编辑、存储、资源文档；没有复制其代码或地址。

| 新证据 | 意义和边界 |
|---|---|
| 拍摄设置编辑状态及其工厂、事件表 | 区分拍摄界面与 RAW 编辑；原表包含 47 个事件、5 个状态，删除键按下、释放、长按均不在字典里 |
| 自有 RAM 中扩展事件表 | 原厂状态机能把删除键送到编辑状态的局部处理器；47 条原事件的目标保持一致，原有 235 个表格单元逐字节保留 |
| 局部处理器 → 控制器 → COLOR 父控件 | 原厂构造实际 COLOR 父对象，再通过明确的控制器外壳重放至父控件入口；不是完整启动、硬件扫描或按键实测 |
| 数值记录的真实读取者 | 新定位到原厂界面消费该记录，数字资源只有六帧；直接把数值查表扩成 ±7 会被原生控件拒绝 |
| 原生文字候选 | 同一界面的原厂记录消费者把自有轴名和数值送到 UTF-16 设置入口；尚未改生产者，未执行字形、绘制或证明画面布局 |
| 提交的反证 | 从完整 GUI 设置接口和真实子控件提交分别重放，均在同一个未建模的 RTOS 上下文读取停止；没有持久化成功结论 |

删除键方案的限制：

- 目前扩表实验只修改私有自有 RAM；没有证明新固件表的放置、加载和 ROM 引用重定向。
- 只扩表会把删除键交给整个设置编辑状态，不能保证其他编辑器不受影响；实现时仍须加入 COLOR 属性键、实例身份及生命周期守卫。
- 原生父控件原本会做事件队列整理；它不是“已经提供轴切换”。本轮停在该控件入口，没有用假成功返回代替轴切换。

显示检查采用两种方法：

1. 从 C3d 诊断、接口槽及“命令 5”的调用者核对，确认绘制传输入口，但没有证明十二色值与共享光标的生产者。
2. 在有界应用代码区检查 GNU 确认的 13 字节复制候选；发现的复制源没有独立 COLOR/C3d 关联，不能因长度相同就当作色轮。

提交停止点是原厂同步对象初始化所需的 RTOS 上下文，具体读地址和 PC 在 JSON。
没有给缺失上下文填零，也没有把准入检查或设置服务替换成成功返回。
这是当前离线夹具的缺口，不证明 E-P7 无法实现机内 H/L；机主无需重复实测空闲按键。
静态交叉引用表明 GUI 值设置与 v4 正常设置最终汇入同一个注册设置核心，但这不足以证明安全的 H/L 事务。

下一次实现的明确约束（尚未实施）：

1. 先补齐有界的 GUI 同步对象/准入夹具，验证忙和闲两类场景；写入必须发生在原厂准入之后。
2. 轴切换重建十二个子控件的枚举及缓存，共用原厂色区光标；进入默认 S，退出清除轴状态，不能向原厂对象插入未对齐字段。
3. H/L 复用 v4 分部写入、刷新及发布；后续 S 协调通知仍携带真实 S，不能把 H/L 值作为 S 传播。
4. ALL 边界和长按 OK 的默认值、提交都作用于当前轴；S 原分支保留，不采用 PR #72 建议的禁用降级。
5. 可先验证原生文字候选替代 H/L 数字与轴标签；仅在其余验收全部完成后，才可按机主授权发布色轮仍显示 S 的 v5a。
